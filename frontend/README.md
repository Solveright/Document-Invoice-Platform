# Phase 7 — Frontend

Vanilla HTML/CSS/JS. No build step, no npm, no framework. Four files:

| File | Purpose |
| --- | --- |
| `index.html` | Markup: sign-in form, dropzone, document list |
| `styles.css` | Styling |
| `app.js` | Cognito auth, presigned upload, document list |
| `config.js` | **Generated by Terraform.** Gitignored. |

## Request flow

```
Browser ──1── Cognito InitiateAuth ──► IdToken (JWT)
Browser ──2── POST /documents  (Authorization: <IdToken>)
                 └─► API GW (JWT authorizer) ─► Lambda
                        ├─ generate_presigned_url(put_object)
                        └─ SQS ─► consumer ─► DynamoDB
Browser ──3── PUT <presignedUrl>  ──────────────► S3 raw bucket
Browser ──4── GET /documents ──► list from DynamoDB
```

Step 3 is the point of the design: file bytes go browser → S3 directly. They
never traverse API Gateway (10 MB payload cap) or Lambda (billed per ms).

## Deploy

```bash
cd infra/terraform
terraform init      # picks up the new hashicorp/local provider
terraform apply
terraform output website_url
```

`apply` writes `frontend/config.js` from live stack outputs, uploads all four
files to the site bucket, and invalidates the CloudFront cache. Changing any
frontend file and re-running `apply` re-uploads it (the `etag` attribute
detects the change) and re-invalidates.

The first `apply` that creates the distribution takes 3–8 minutes — CloudFront
propagates to every edge location before returning. Subsequent applies are
fast unless you change the distribution itself.

As of Phase 8 the site is served from CloudFront over HTTPS and the bucket is
private. There is no S3 website endpoint any more; hitting the bucket directly
returns 403, which is the point.

## Local development

```bash
cd frontend
python -m http.server 8000
```

Then open <http://localhost:8000>. `http://localhost:8000` is already in
`var.local_dev_origins`, so it is allowed by both the API Gateway CORS config
and the raw bucket CORS rule. Opening `index.html` via `file://` will **not**
work — the origin is `null` and every CORS check fails.

## Creating a test user

```bash
POOL_ID=$(terraform -chdir=infra/terraform output -raw cognito_user_pool_id)

aws cognito-idp admin-create-user \
  --user-pool-id "$POOL_ID" \
  --username seth \
  --user-attributes Name=email,Value=you@example.com Name=email_verified,Value=true \
  --message-action SUPPRESS \
  --temporary-password 'TempPass123'
```

Sign in with the temporary password; the UI handles the
`NEW_PASSWORD_REQUIRED` challenge and prompts for a permanent one.

## Known limitations (deliberate — these are later phases)

- **No custom domain.** The site lives at `https://dxxxx.cloudfront.net` on
  CloudFront's default certificate. Phase 9 adds Route 53 and an ACM cert —
  which must be issued in `us-east-1` regardless of where the bucket lives.
  **Always run `terraform apply -var-file "test.tfvars"` (see `infra/terraform/`)
  — a bare `apply` without it drifts against the live `test.solveright.com.tw`
  ACM cert and will destroy it.**
- **Status is `PENDING_UPLOAD`, not `PROCESSED`.** The API enqueues the SQS
  message when it hands out the presigned URL, so the consumer usually writes
  the DynamoDB item *before* the browser finishes the PUT. Phase 10 replaces
  this with an S3 `ObjectCreated` event, which only fires once the object
  actually exists.
- **`USER_PASSWORD_AUTH`, not SRP.** The password goes to Cognito over TLS
  rather than being proven via SRP. Switching to SRP means pulling in
  `amazon-cognito-identity-js`, which means a bundler.
- **Tokens in `sessionStorage`.** Readable by any XSS on this origin. The
  production answer is the Cognito hosted UI with authorization code + PKCE.
- **No token refresh.** The app client is configured for
  `ALLOW_REFRESH_TOKEN_AUTH` but the UI does not use it — when the IdToken
  expires (1h default) you are signed out and re-authenticate.
- **`GET /documents` returns one 50-item page**, sorted in Lambda by
  `uploadedAt`. The table's sort key is `documentId` (a UUID), so DynamoDB's
  native ordering is meaningless. A GSI on `(userId, uploadedAt)` is the real
  fix — noted for Phase 13.

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| `403 SignatureDoesNotMatch` on the PUT | The `Content-Type` header sent by the browser does not match the one baked into the signature. Both must be `application/pdf`. |
| CORS error on the PUT | Origin missing from `aws_s3_bucket_cors_configuration.raw_documents`. Check `terraform output allowed_origins`. |
| CORS error on `POST /documents` | Same, but for the API Gateway `cors_configuration`. Origins match byte-for-byte including port. |
| `401` from the API | Sending the AccessToken instead of the IdToken. The authorizer validates `aud` against the app client ID, and only the IdToken carries `aud`. |
| Browser downloads `index.html` instead of rendering it | `content_type` missing on the S3 object. |
| Old JS still served after `apply` | CloudFront cache. `apply` invalidates automatically unless `enable_cloudfront_invalidation = false`; otherwise wait out `max-age=300` or invalidate by hand with `cloudfront_distribution_id`. |
| `403 AccessDenied` XML from CloudFront on every path | Bucket policy `AWS:SourceArn` doesn't match the distribution, or the OAC isn't attached to the origin. |
| Any path except `/` returns an error page | `custom_error_response` missing. The S3 REST origin has no `index_document`; 403/404 must be mapped back to `/index.html`. |
| Cognito or upload calls blocked in console | `enable_csp = true` with a `connect-src` that doesn't cover the host. Check the exact blocked URL in the console error. |
